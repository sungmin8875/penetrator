4시뮬레이션 로직

용량 제약 하의 매출 우선 그리디(월 단위) 할당 — Palantir 알고리즘 그대로, 입력만 더 정직해졌습니다. 아래는 실행 1회의 실제 처리 순서입니다.

4.1 순수요 계산 (net_production_demand)

  • 선택된 리비전의 이동계획을 모델×월로 집계. model_id='기타매출' 행은 «기타매출» 카테고리로 분리되어 생산 대상에서 제외.
  • 재고 상쇄는 총재고 = 보유(FGI) + 이동중(FGI-TRN) + 출하 프레임에서 출발 — 엔진이 이동중 수량을 총재고 − 출하 − 보유로 역산하므로 출하가 총계 안에 있어야 함(빠지면 이동중이 정확히 출하량만큼 음수가 되는 함정).
  • Forward rolling: 이른 월의 잉여 재고가 다음 월 수요를 상쇄. 결과 = 모델×월 순생산 필요량(EA). 로그의 "Inventory consumed" 블록이 이 단계의 감사 출력.

4.2 우선순위 (target_step 임계비)

  • 모델×월마다 priority = dense_rank(잔여 스텝 수 ÷ 납기까지 잔여 일수, 내림차순) — 갈 길이 먼데 시간이 없는 모델이 먼저. MES 우선도 피드가 없는 상황의 고객 합의 규칙.
  • 이월 수요는 priority=99999999로 밀려 해당 월의 신규 수요를 모두 처리한 뒤 시도됨.
  • 가중 방식(weight_revenue/margin/delivery)은 코드가 존재하지만 명시적 옵트인 전용 — 플로우가 기본 가중치를 항상 보내므로 값 존재만으로 켜지지 않게 봉인되어 있음.

4.3 Phase 0 — 긴급 랏 선처리 (urgent_allocation, MLWB 추가)

  • UrgencyWipLot에 등록된 재공 랏을 생성일 오래된 순으로, 월별 루프 이전에 잔여 라우팅 끝까지 할당.
  • 목표월은 랏의 실제 납기(ReceiptTargetDay, ~58% 충전)를 우선 사용, 없으면 시작월.
  • 긴급 랏의 생산량은 해당 모델의 월 수요에 크레딧되어(로그의 "Phase 0 credit") 같은 수요로 중복 랏이 생기지 않음. HOLD 제외와 충돌하는 긴급 랏은 스케줄되지 않고 경고 로그로 표면화(HOLD 우선).

4.4 월별 그리디 루프 (시작월 → +3개월)

  • 각 월에서 모델을 우선순위 순으로 처리. 모델당 필요량 = 해당 월 순수요 + 이월분.
  • Phase 1 — 기존 재공 랏: 그 모델의 재공 랏 중 필요량 × 1.1 버퍼를 채울 만큼만 선별(로그 "Selected N of M lots"). 각 랏은 현재 위치부터의 잔여 라우팅 스텝 전체를 순서대로 할당 시도. 한 스텝이라도 실패하면 랏 전체가 실패 처리(부분 진행 없음).
  • Phase 2 — 가상 랏(VL): Phase 1 이후 부족분을 패널로 환산해 maximum_lot_size_pnl(모델 LotSize, EA→SHT 변환 검증됨: LotSize÷EaInSheet ≈ 5 SHT) 단위로 분할 생성. 각 VL은 모델 라우팅 전체를 스텝으로 받고, 시작일은 그루핑 모델별 JIG 랏 착수율로 스로틀됨(하루에 무한 착수 방지).
  • 이월 의미론(중요): 수요는 «정시 완료» 기준이 아니라 «할당(스케줄)됨» 기준으로 충족 처리 — 지연되더라도 일단 스케줄된 수요는 다음 달에 다시 랏을 만들지 않음. 할당 불가분만 "Carrying forward"로 이월.

4.5 스텝 1건의 할당 (allocation_engine 코어)

  • 후보 결정: 스텝의 OperationCode로 포지티브 배정표(equipment_to_process)에서 설비 후보 조회. 후보가 없으면 → ① 논리 공정(M000N LOT START 등)은 0일 통과 ② 그 외는 외주 분기(4.6) ③ 외주 토글 OFF일 때만 원본의 FAILED_NO_EQUIPMENT.
  • 시작일: 랏의 직전 스텝 완료일(첫 스텝이면 목표 착수일과 실행 시작일 중 늦은 쪽).
  • 일자 전진 탐색: 시작일부터 하루씩, 후보 설비마다 해당일 사용량 + 스텝 SHT ≤ DailyCapa 검사. 자리가 나는 첫 (일자, 설비)에 배정하고 사용량을 적립. 랏당 하루 최대 스텝 수(max_steps_per_lot_per_day) 제한이 같은 랏의 연쇄 배정을 막음.
  • 실패 조건: max_delay_days(운영 90일)까지 자리가 없으면 FAILED_INSUFFICIENT_CAPACITY, 탐색이 계획 지평선을 넘으면 FAILED_HORIZON_EXCEEDED. 대기한 날마다 DelayRecord가 쌓여 분석(4.7)의 원료가 됨.
  • ⚡ 스캔 메모(scan_memo, MLWB 추가): 용량 사용량이 실행 중 단조 증가한다는 불변식을 이용한 2단 캐시 — L1 스텝 SHT가 후보 설비 최대 총용량을 초과하면 즉시 동일 판정으로 실패(과대 VL 사전판정), L2 (공정, 차단셋, 일자)별로 «q SHT 못 들어감이 증명된 최소 q»를 메모해 같은 날 재스캔 생략. 배정 결과·날짜·상태 전부 바이트 동일(7 시나리오 A/B + 6,000스텝 혼합 검증), 지연 사유 문자열만 요약형으로 얇아짐.

4.6 외주 패스스루 (outsourced_allocation, 고객 규칙 2026-07-15)

  • 규칙: 설비 매핑 없음 = 외주(외주 공정은 RTS가 설비 계획을 안 하므로 매핑 부재가 정상 상태). 스텝은 용량 소모 없이 «계획 완료» 처리되고 랏은 다음 스텝으로 진행.
  • 소요시간 체인(우선순위순): ① WipHistory 실측 중앙값(모델×공정 → 공정 단독, measured_lt ON일 때) ② 라우팅 PlanLt(99.1% 충전) ③ RunLt×SHT + WaitLt(시간) ④ 기본값. 시간→일 환산은 24h/일(연속 가동).
  • 이상치 캡: outsourced_step_max_days(기본 30일) 초과 스텝은 캡 + 감사 카운트(라우팅 쓰레기 값이 랏을 2082년으로 보낸 사고의 방어).
  • 완료일이 랏의 last-step date로 기록되므로 외주 리드타임은 실제 경과시간으로 작동(다음 스텝은 벤더 복귀 후 시작). equipment_id='OUTSOURCED' 스탬프 + 실행당 공정별 감사 목록 출력 — 이 목록의 사내 공정 = 매핑 누락 신호.

4.8 마스터 출력 빌드 (run_simulation, MLWB 추가)

  • SimWIPMaster = SimAllocation(랏×스텝) + WipHistory 랏 실적 요약(lot_id 조인: 실측 최초 착공/최종 이벤트/실수량/양산·시재) + 라우팅 (모델, 공정, WorkSeq) 조인의 CHASU·GubunColumn. 실적 없는 랏(VL 포함)은 실적 컬럼 null.
  • SimStockMaster = 자재×일자 원장: 보유량 = initial_onhand_qty + 누적 보충 − 누적 사용, 입고 제외 곡선(balance_qty_wo_arrivals)과의 차 = PO 입고 리스크. 사용량은 CopClass 규칙(§3 cop_usage) 적용 후 집계. 자재별 첫 활동일 −1일에 앵커 행(차트 시작점).

확인된 병목(수 차례 입력 개선에도 불변): 13.Laser / M717N이 제1 병목, 5.도금 (M510N/M710N)이 제2 병목. DailyCapa 중앙값 5 SHT vs VL ~30 SHT 구조로 공장이 실제 포화 상태.

6데이터 한계와 알려진 편향

시뮬레이션의 산식은 Palantir와 동일하므로, 신뢰도의 상한은 아래 입력 한계가 결정합니다. 심각도는 결과 왜곡 방향(대부분 낙관)에 대한 평가입니다.

심각도한계영향대응 / 필요 조치
높음설비 매핑 커버리지 — 라우팅 398개 공정 중 126개(31.7%)만 설비 보유. 271개 실공정 + 비활성 필터로 전멸한 22개 공정이 «외주 간주» 무료 통과(실행당 ~35만 스텝).낙관 — 실제 사내 공정이면 용량 소모가 누락됨.매 로그의 OUTSOURCED-ASSUMED 감사 목록을 LG와 검토, 사내 공정(F1/F2 사이트) 매핑 보완. WipHistory EQPTID 대조가 검증 수단.
높음RAW-MTL 재고 피드 커버리지 — 활성 자재 다수가 OnHand에 레코드 없음(385개 자재만 보유).자재 쇼티지가 재고 부족이 아니라 데이터 부재로 계산될 수 있음.재고 피드 범위 확대를 LG에 요청(핵심 데이터 ask).
중간PO 입고 계획 = 추정치, ReceiptTargetDay 충전율 ~58%.보충량·긴급랏 목표월의 신뢰도 제한.StockMaster의 balance_qty_wo_arrivals와의 갭으로 리스크를 명시적으로 보여줄 것.
해결HOLD 랏 — 과거엔 홀드 랏(재공의 36.6%)을 가용 공급으로 계산.해결됨: exclude_hold 기본 ON. 긴급∩홀드 충돌(90랏)은 경고 로그로 표면화.URGENT∩HOLD 목록은 데이터 품질 이슈로 LG 보고 가치 있음.
해결비활성 설비 — Palantir는 ActiveFlag를 안 걸렀던 것으로 추정(빠른 실행 = 유령 용량).해결됨: 2,266대 제외. 그 결과 공장이 «정직하게» 포화 — 실행 시간 문제는 스캔 메모로 해소.

남은 오픈 항목 (LG 확인 대기)

  • max_delay_days 현실값(현재 90 운영).
  • CopClass 집계 규칙의 범위 — 차트 전용(현재) vs 고갈 분석까지 적용.
  • 잔여 추출 테이블: PO_INFO > PRODUCTION_RESULT > Sales Plan 순 우선.
  • VL 랏 크기(현 ~30 SHT)의 현실성 — DailyCapa 중앙값 5와의 구조적 긴장.

7운영 체크리스트

  • 정상 실행 시간: 약 7분(읽기→쓰기 전체). 밤샘 실행이 재발하면 scan_memo가 OFF인지, 수요 리비전이 비정상인지부터 확인.
  • 프론트에 새 실행이 안 보이면: ① 데이터 모델 로드가 push 이후에 돌았는지(풀 append ≠ 모델 반영) ② 보고 있는 퍼스펙티브가 test 트윈인지 ③ run_id 필터. 순서대로 확인 — 셋 중 하나가 원인이었던 전례뿐임.
  • 로그 읽는 법: 각 실행 로그의 감사 라인이 상태 요약입니다 — HOLD 제외 수, CopClass 규칙 분포(A/B/C/D 매칭 0이면 값 체계 변경 의심), OUTSOURCED-ASSUMED 목록, 측정 LT 설치 수, 스캔 메모 ON/OFF.
  • 출력 스키마를 바꿀 때: 해당 테이블명을 REVPLAN_SCHEMA_MIGRATE에 넣고 1회 실행(그 테이블만 이력 소실) → 성공 로그 확인 → 반드시 다시 비우기. 플랫폼이 스키마 불일치 append를 조용히 «합집합»으로 받는 사고가 있었으므로, 실패 대기 방식은 쓰지 말 것.
  • MLWB 파일 동기화: 저장소가 진실의 원천. MLWB 폴더에 파일을 부분 복사하면 버전 스큐로 AttributeError가 납니다 — 변경된 파일 목록을 git diff로 뽑아 전부 복사할 것.
  • 프론트 관계 설정: StockMaster↔Material(N:1)은 안전. PoArrivePlan/BOM은 Material 허브 경유 + 드릴다운 권장(직접 관계는 팬아웃). 자재↔랏 브리지는 SIM_material_consumption_events.
