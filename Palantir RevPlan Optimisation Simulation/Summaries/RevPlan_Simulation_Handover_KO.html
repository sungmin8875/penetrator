1전체 아키텍처

한 번의 버튼 클릭 = 한 번의 시나리오 실행. 핵심 할당 엔진은 Palantir 소스의 바이트 단위 사본이며, MLWB 추가/변경 코드는 전부 ⚠️ MLWB ADDITION/DIVERGENCE 주석 블록으로 표시되어 있습니다.

Studio 화면→ Action Flow (/executions 파라미터)→ MLWB 노트북 (papermill)→ revplan_engine→ SIM_* 테이블 append→ OE finish-simulation 이벤트→ 데이터 모델 로드 → 프론트
파일역할
run_revplan_simulation.ipynb실행 진입점. 셀 1 = papermill 파라미터, 셀 5 = 파라미터 정규화 + 토글 환경변수 설정, 셀 6–8 = read → run → write, 셀 9 = OE 재개 이벤트.
revplan_engine/celonis_io.pyCelonis 결합 전체: 연결, TABLE_MAP/COLUMN_MAP, read_inputs(입력 17종), write_outputs(append-only 이력, 리스트 컬럼 평탄화, 스키마 마이그레이션 게이트).
revplan_engine/run_simulation.py오케스트레이터. 순수요 → 우선순위 → 할당 → 분석 5종 → SimWIPMaster/SimStockMaster 빌드(CopClass 규칙 포함).
allocation_engine.py 외 헬퍼Palantir 원본 사본(수정 = 마킹된 블록만). 스캔 메모 최적화, 외주 훅, 긴급 프리패스가 여기에 게이트로 삽입되어 있음.
outsourced_allocation.py / urgent_allocation.py / priority_generation.pyMLWB 신규 모듈: 외주 패스스루, Tier-1 긴급 랏 선처리, 가중 우선순위(기본 OFF).
orchestration.pyOE 메시지 API로 finish-simulation CloudEvent 발신(인스턴스 재개).

데이터 모델: 노트북은 test:perspective_custom_Simulation (ID 6570e74c-ff78-464e-bd16-142101117d26)을 사용합니다. 동일 오브젝트의 쌍둥이 퍼스펙티브(73bc8779-…)가 존재하므로, 프론트 화면과 노트북이 같은 퍼스펙티브를 보는지 항상 확인하세요 — "테이블이 프론트에는 보이는데 엔진이 못 읽는" 문제의 원인이었습니다. 환경변수 CELONIS_DATA_MODEL로 전환 가능합니다.

2데이터 배선 — 무엇을 어디서 읽어 무엇에 쓰는가

모든 소스는 OCPM 오브젝트(o_custom_*)이며, celonis_io.TABLE_MAP / COLUMN_MAP이 원본 PPS/RTS 테이블명·컬럼명과의 대응을 정의합니다. 컬럼 이름이 오브젝트 SQL에서 바뀌면 여기만 고치면 됩니다.

3설정 — 노트북 파라미터와 토글

운영 실행은 Action Flow가 /executions 파라미터로 노트북 셀 1을 덮어쓰는 방식입니다. 셀 5가 모든 값을 관용적으로 파싱하므로(null·빈문자·쓰레기 → 기본값 + 경고) 플로우 필드가 비어도 실행이 죽지 않습니다.

파라미터기본값의미

4시뮬레이션 로직

용량 제약 하의 매출 우선 그리디(월 단위) 할당 — Palantir 알고리즘 그대로, 입력만 더 정직해졌습니다.

  • ① 순수요. 이동계획 수요 − (출하 + 보유 + 이동중 재고), forward-rolling으로 월별 상쇄 → 모델×월 순생산 필요량.
  • ② 우선순위. 기본 target_step: 잔여 스텝 ÷ 잔여 일수(임계비, 납기 기준). MES 우선도·마진 소스가 없어 가중 방식은 봉인(옵트인).
  • ③ Phase 0 — 긴급 랏. UrgencyWipLot의 랏을 생성일 오래된 순으로 선할당. 생산량은 해당 모델 수요에 크레딧.
  • ④ 월별 루프(시작월→+3개월). 모델을 우선순위 순으로: Phase 1 기존 재공 랏 할당(1.1× 버퍼로 선별) → 부족분은 Phase 2 가상 랏(VL) 생성(LotSize 기준 분할) → 미충족분은 익월 이월(이월은 «할당됨» 기준 — 중복 랏 생성 방지).
  • ⑤ 스텝 할당. 랏의 잔여 라우팅을 스텝별로: 후보 설비(포지티브 배정표)에서 일자를 전진 탐색하며 DailyCapa(SHT) 잔여를 확인, max_delay_days 초과 시 FAILED_INSUFFICIENT_CAPACITY. 랏당 일일 스텝 상한, 호라이즌 초과 시 FAILED_HORIZON_EXCEEDED.
  • ⑥ 외주 패스스루(고객 규칙 2026-07-15). 설비 매핑이 없는 공정 = 외주로 간주: 용량 소모 없이 소요시간(실측 LT → PlanLt → RunLt×SHT+WaitLt → 기본값, 상한 캡)만큼 진행 후 다음 스텝. equipment_id='OUTSOURCED'로 스탬프 — 감사 목록이 매 로그에 출력됨.
  • ⑦ 분석 5종. 설비 용량 부족(연속 구간)·랏 대기 · ET-JIG 리스크 · 자재 고갈(BOM×할당 소요, 총보유 기준 1회 차감, 차수 라벨) · 수요 쇼티지 귀속 · 생산 리스크 정산(LEAD_TIME / ET_JIG / EQUIPMENT 3분류 수지 일치 검증).
  • ⑧ 마스터 출력 빌드. SimWIPMaster(할당×WipHistory 실적×라우팅 CHASU/Gubun), SimStockMaster(자재×일자 피벗, CopClass 규칙 적용).

확인된 병목(수 차례 입력 개선에도 불변): 13.Laser / M717N이 제1 병목, 5.도금 (M510N/M710N)이 제2 병목. DailyCapa 중앙값 5 SHT vs VL ~30 SHT 구조로 공장이 실제 포화 상태.

push 동작: 문자열 컬럼 폭은 최초 생성 시 실측×2(최소 256, 최대 4000)로 설정, 이후 append는 그 폭 안에서만. polars List 컬럼은 push 직전 쉼표 문자열로 자동 평탄화(중첩 Parquet 거부 대응). 일시적 400 오류는 1회 재시도. append 실패 시 테이블을 절대 자동 drop하지 않음 — §3의 마이그레이션 절차를 따르세요.

6데이터 한계와 알려진 편향

시뮬레이션의 산식은 Palantir와 동일하므로, 신뢰도의 상한은 아래 입력 한계가 결정합니다. 심각도는 결과 왜곡 방향(대부분 낙관)에 대한 평가입니다.

심각도한계영향대응 / 필요 조치
높음설비 매핑 커버리지 — 라우팅 398개 공정 중 126개(31.7%)만 설비 보유. 271개 실공정 + 비활성 필터로 전멸한 22개 공정이 «외주 간주» 무료 통과(실행당 ~35만 스텝).낙관 — 실제 사내 공정이면 용량 소모가 누락됨.매 로그의 OUTSOURCED-ASSUMED 감사 목록을 LG와 검토, 사내 공정(F1/F2 사이트) 매핑 보완. WipHistory EQPTID 대조가 검증 수단.
높음수율 미반영 — 투입/적용/타입 수율이 소요·산출 어디에도 안 곱해짐.낙관 — 자재 소요 과소, 산출 과대.모델 오브젝트에 수율 컬럼 존재 확인됨("모델 정보에 수율이 다 있어요") — 수율 3종 결합 산식을 LG에 확인 후 적용(플래그 자리 enable_yield_loss 준비됨).
높음RAW-MTL 재고 피드 커버리지 — 활성 자재 다수가 OnHand에 레코드 없음(385개 자재만 보유).자재 쇼티지가 재고 부족이 아니라 데이터 부재로 계산될 수 있음.재고 피드 범위 확대를 LG에 요청(핵심 데이터 ask).

중간양산/시제 판별 규칙 미확정 — 미팅에서 "그루핑 모델 기준"이라고만 확인.SimWIPMaster의 aps_prodcategory(MES 원본값)로 임시 대응.유력 가설: 접미 코드 .KM*=양산, .K+숫자=시제 — WipHistory와 교차 검증 또는 LG 확인 필요. 시제율 예약 정책(10–20%, 전체/공정별)도 미정.

7운영 체크리스트

  • 정상 실행 시간: 약 7분(읽기→쓰기 전체). 밤샘 실행이 재발하면 scan_memo가 OFF인지, 수요 리비전이 비정상인지부터 확인.
  • 프론트에 새 실행이 안 보이면: ① 데이터 모델 로드가 push 이후에 돌았는지(풀 append ≠ 모델 반영) ② 보고 있는 퍼스펙티브가 test 트윈인지 ③ run_id 필터. 순서대로 확인 — 셋 중 하나가 원인이었던 전례뿐임.
  • 로그 읽는 법: 각 실행 로그의 감사 라인이 상태 요약입니다 — HOLD 제외 수, CopClass 규칙 분포(A/B/C/D 매칭 0이면 값 체계 변경 의심), OUTSOURCED-ASSUMED 목록, 측정 LT 설치 수, 스캔 메모 ON/OFF.
  • 출력 스키마를 바꿀 때: 해당 테이블명을 REVPLAN_SCHEMA_MIGRATE에 넣고 1회 실행(그 테이블만 이력 소실) → 성공 로그 확인 → 반드시 다시 비우기. 플랫폼이 스키마 불일치 append를 조용히 «합집합»으로 받는 사고가 있었으므로, 실패 대기 방식은 쓰지 말 것.
  • smoke_test.py: 참조용으로만. T4는 et_jig_master 픽스처 부재로 실패하는 기지 이슈이며, 이 파일은 수정하지 않는 것이 프로젝트 관례.
  • MLWB 파일 동기화: 저장소가 진실의 원천. MLWB 폴더에 파일을 부분 복사하면 버전 스큐로 AttributeError가 납니다 — 변경된 파일 목록을 git diff로 뽑아 전부 복사할 것.
  • 프론트 관계 설정: StockMaster↔Material(N:1)은 안전. PoArrivePlan/BOM은 Material 허브 경유 + 드릴다운 권장(직접 관계는 팬아웃). 자재↔랏 브리지는 SIM_material_consumption_events.
