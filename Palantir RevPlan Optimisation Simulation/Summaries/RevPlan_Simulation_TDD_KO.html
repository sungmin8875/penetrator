Section 1: 프로세스 개요

1.1문서의 목적

본 기술설계문서는 LG Innotek을 위해 Celonis 플랫폼에 구현된 RevPlan 최적화 시뮬레이션의 설계와 구축 내용을 설명합니다. 컨설턴트가 처음부터 솔루션을 재구축할 수 있을 만큼 상세하게 작성되었으며(부록 C 재구축 체크리스트 포함), Section 1~2만으로 리더십 수준의 요약 자료로도 활용할 수 있습니다. 컬럼 단위 상세(전 SIM_ 테이블의 컬럼 사전)는 별도의 인수인계 문서 §5.1에 있으며, 본 문서와 한 세트입니다.

1.2비즈니스 배경 및 문제 정의

LG Innotek 기판(substrate) 사업은 이동계획(Move Plan)이 갱신될 때마다 "이 계획을 현재 공장이 실제로 소화할 수 있는가"를 알아야 합니다 — 어느 모델이 목표월을 놓치는지, 병목이 어느 공정인지, ET-JIG·자재는 충분한지. 이 시뮬레이션은 원래 Palantir Foundry에 UC2-2 «시나리오 베이스 시뮬레이션»으로 구축되어 있었으나, Foundry 계약 종료에 따라 Celonis EMS로 이관이 필요했습니다. 요구사항은 단순 이관을 넘어, Palantir 시절 검증되지 않았던 입력 데이터 문제(유령 설비, 홀드 랏, 스냅샷 그레인 오류)의 교정까지 포함합니다.

1.3솔루션 요약

Studio 화면에서 시나리오(이동계획 리비전, 시작월, 최대 지연일 등)를 선택하면, Action Flow가 MLWB 노트북을 트리거하고, 노트북 안에서 Palantir 할당 엔진의 바이트 단위 사본이 실행됩니다: Celonis 오브젝트에서 17종 입력을 읽고 → 순수요를 계산하고 → 용량 제약 하의 그리디 할당을 수행하고 → 분석 6종을 산출하여 → 20개의 SIM_ 테이블로 Data Pool에 append합니다. 완료 시 OE 이벤트로 오케스트레이션이 재개되고, 데이터 모델 재로드 후 Studio 대시보드에 결과가 나타납니다. 한 번의 버튼 클릭 = 하나의 시나리오 = 약 7분입니다.

핵심 설계 원칙: 할당 수학은 Palantir 원본과 동일하게 유지하고(재동기화 가능), 모든 변경은 ⚠️ MLWB ADDITION/DIVERGENCE 마킹 블록 + 토글(킬스위치)로 격리합니다. 따라서 어떤 실행이든 토글을 끄면 원본 동작으로 되돌릴 수 있습니다.

1.5용어 정의 (Glossary)

용어의미
이동계획 (Move Plan)단기 생산/출하 계획 = 시뮬레이션의 수요 입력. 리비전(RevisionNo) 단위로 갱신되며, 실행 시 하나를 선택.
VL (가상 랏)기존 재공으로 못 채우는 수요에 대해 엔진이 생성하는 Virtual Lot. lot_id = VL-{모델}-{월}-{해시}.
차월 원칙시작월 미지정 시 다음 달부터 계획 (Palantir 원칙 — 당월 실행은 남은 일수에 한 달 수요를 압축해 폭주).
target_step기본 우선순위 규칙: 잔여 공정 수 ÷ 납기까지 잔여 일수 (임계비). 고객 확정 실무 규칙.
외주 패스스루설비 매핑 없는 공정 = 외주 간주 (고객 규칙 2026-07-15): 용량 소모 없이 소요시간만큼 진행. equipment_id='OUTSOURCED'.
스캔 메모포화일 재탐색 제거 최적화 (결과 바이트 동일, 6~40× 가속) — 밤샘 런타임의 해결책.
HOLD 제외최신 스냅샷 기준 STATE=HOLD/WIPHOLD=Y 재공 랏을 스케줄에서 제외 (재공의 ~36%가 홀드).
append-only 이력모든 SIM_ 테이블은 실행마다 append — 조회는 반드시 allocation_run_id로 한 실행을 필터.
CopClass 집계 규칙자재 등급별 소요 계상 시점: A→SEQ2, B→M510N, C→M520N 통과일, D 제외 (StockMaster 전용).
이월 (Carryover)미충족 수요의 익월 재시도. «할당됨 = 충족» 기준이라 지연 랏은 중복 생성되지 않음.

2.3솔루션 아키텍처

Studio 화면 (시나리오 입력)→ Action Flow (/executions 파라미터)→ MLWB 노트북 (papermill)→ revplan_engine (할당 + 분석)→ SIM_* append (Data Pool)→ finish-simulation 이벤트→ DM 재로드 → 대시보드

OE 프로세스 흐름 — 각 Process step은 Action Flow가 뒷받침하며, Resume은 이벤트를 대기합니다:

#단계유형설명 / 대기 대상
1start-simulation-oeStart eventStudio 폼 제출이 발생 — 시나리오 파라미터를 페이로드로 전달.
2Create OE TableProcess stepSIMULATION_OE_Table에 인스턴스 행 생성 (dpInstanceId 키, 파라미터 스냅샷).
3Trigger MLWBProcess stepPOST /machine-learning/api/executions — 노트북 실행, params에 dpInstanceId + 시나리오 값 주입 (부록 A).
4simulation doneResume노트북 마지막 셀이 ce-instanceid=dpInstanceId로 finish-simulation을 발생시킬 때까지 대기.
5Trigger DM reloadProcess step데이터 모델 재로드 — 새 SIM_ 행이 프론트에 반영되는 시점.
6Load-finished alertProcess step재로드 완료 알림 (담당자 통지용 플로우).
노트북은 데이터 모델을 재로드하지 않습니다. Pool append ≠ 프론트 반영 — 재로드는 OE의 별도 단계이며, "새 실행이 화면에 안 보인다"는 문의의 1순위 원인이 이 시차입니다 (§4.6).

3.4.1 push 메커니즘 (write_outputs)

  • append-only 이력: 최초 실행 시 생성, 이후 append — 절대 drop하지 않음. 조회는 allocation_run_id 필터 필수.
  • 문자열 폭: 생성 시 실측×2 (최소 256, 최대 4000)로 column_config 지정 — 이후 append는 그 폭 안에서.
  • 리스트 컬럼 평탄화: polars List 컬럼은 push 직전 쉼표 문자열로 자동 변환 (플랫폼이 중첩 Parquet 거부 — *_ids 컬럼들이 400으로 죽던 원인).
  • 재시도: 일시적 400(Parquet validation)은 5초 후 1회 재시도.
  • 스키마 변경 절차: 해당 테이블명을 REVPLAN_SCHEMA_MIGRATE에 넣고 1회 실행(그 테이블만 재생성·이력 소실) → 성공 확인 → 반드시 다시 비움. append 실패 대기 방식은 금지 — 플랫폼이 스키마 불일치를 조용히 «합집합»으로 받은 사고가 있음.
  • 플레이스홀더 가드: dpInstanceId가 'local-test' 등이면 push 전체 스킵 (오염 방지; 개발 강제는 CELONIS_ALLOW_PLACEHOLDER_WRITE=1).

Section 4: 시뮬레이션 엔진

4.1알고리즘 상세

4.1.1 순수요 (net_production_demand)

  • 선택 리비전의 수요(모델×월)에서 재고 상쇄: 총재고 = 보유(FGI) + 이동중(FGI-TRN) + 출하. 출하가 총계 안에 있어야 함 — 엔진이 이동중을 총재고−출하−보유로 역산하므로.
  • Forward rolling: 이른 달 잉여가 다음 달 수요를 상쇄. model_id='기타매출'은 생산 제외.
  • 차감 그레인 주의: 구조는 그룹핑 모델 기준이나 현재 소스에 GroupingModel 값이 없어 개별 MODEL_NO로 동작 (파생 버전 간 재고 상호 대체 없음 — §4.4).

4.1.2 우선순위 (target_step)

  • priority = dense_rank(잔여 스텝 ÷ 잔여 일수, 내림차순) — 월 내 랭킹. 이월분은 99999999로 후순위.
  • 가중 방식(매출/마진/납기)은 명시적 옵트인 전용 — 플로우가 가중치를 항상 보내므로 값 존재만으로 켜지지 않게 봉인.

4.1.3 Phase 0 — 긴급 랏

  • UrgencyWipLot 랏을 등록일 오래된 순으로 월별 루프 전에 완주 할당. 생산량은 해당 모델 수요에 크레딧(중복 랏 방지). 목표월 = ReceiptTargetDay(충전율 ~58%) 우선.

4.1.4 월별 그리디 루프 (시작월 → +3개월)

  • Phase 1 (재공): 필요량 × 1.1 버퍼만큼 랏 선별 → 잔여 라우팅 전체 할당 시도. 한 스텝 실패 = 랏 전체 실패 (단, 실패 전 스텝의 기록·용량 소모는 유지).
  • Phase 2 (VL): 부족분을 LotSize(EA→SHT 검증: ÷EaInSheet ≈ 5 SHT) 단위로 분할 생성, 시작일은 그루핑별 착수율로 스로틀.
  • 조기 종료: 루프 조건이 units_fulfilled < total_demand라서 수요 충족 시 진행 중이던 버퍼 초과 랏은 중단(abandoned) — 실패도 성공도 아닌 제3 상태 (§4.5).
  • 이월: «할당됨 = 충족». 미할당분만 익월에 새 lot id의 VL로 재시도 → 실패 랏 수가 수요 대비 최대 4배까지 부풀 수 있음. 윈도우 마지막 달에서 종료.

4.1.5 스텝 1건의 할당 (코어)

  • OperationCode → 포지티브 배정표에서 설비 후보. 후보 없음 → ① 논리 공정 0일 통과 ② 외주 분기(4.1.6) ③ (외주 토글 OFF일 때만) FAILED_NO_EQUIPMENT.
  • 직전 스텝 완료일부터 하루씩 전진하며 사용량+SHT ≤ DailyCapa인 첫 (일,설비)에 배정. 랏당 일일 스텝 상한.
  • 실패: max_delay_days(운영 90일) 내 자리 없음 → FAILED_INSUFFICIENT_CAPACITY (병목 공정을 지목 — 증설로 해결 가능한 유형); 날짜가 계획 지평선 초과 → FAILED_HORIZON_EXCEEDED (리드타임이 달력을 초과 — 계획 시점의 문제). 두 상태는 같은 지각의 두 문턱이며 config가 상태 간 이동을 만듦 — 집계는 합산, 진단은 분리.
  • 스캔 메모 (⚡): 실행 중 용량 사용량이 단조 증가한다는 불변식을 이용 — L1: 스텝 SHT가 후보 최대 총용량 초과 시 즉시 동일 판정 실패, L2: (공정,차단셋,일)별 «못 들어감이 증명된 최소 수량» 메모. 결과 바이트 동일 검증 완료(7 시나리오 A/B + 6,000스텝), 6~40× 가속.

4.1.6 외주 패스스루

  • 규칙: 설비 매핑 없음 = 외주 (외주 공정은 RTS가 설비 계획을 안 하므로 매핑 부재가 정상). 용량 소모 없이 «계획 완료» 후 다음 스텝.
  • 소요시간 체인: ① WIP 실측 중앙값 (모델×공정 → 공정 단독; measured_lt ON) ② 라우팅 PlanLt (99.1% 충전) ③ RunLt×SHT+WaitLt ④ 기본값. 24h/일 환산, 상한 30일 캡(2082년행 랏 사고 방어) + 캡 감사 출력.
  • 완료일이 랏 last-step date로 기록 → 외주 리드타임은 실제 경과시간. 실행마다 OUTSOURCED-ASSUMED 감사 목록 출력 — 이 목록의 사내(F1/F2) 공정 = 매핑 누락 신호.

4.5결과 해석 가이드

  • 랏 3분류: 완주 = units_produced > 0인 lot (최종 스텝에만 기록됨 — DISTINCT lot 카운트에 CASE로 사용) · 실패 = failed_allocations의 lot · 중단 = 수요 충족으로 방치된 버퍼 초과 랏(양쪽 어디에도 없음). SIM_allocation의 distinct lot 수는 «시도»이지 «성공»이 아님 — 실패 랏도 실패 전 스텝이 남습니다.
  • 실패 랏 수는 재시도로 부풀어 있음: 이월이 매달 새 VL을 만들므로 수요 1건이 실패 랏 최대 4건. 헤드라인은 SIM_demand_shortfall(모델×월, 중복 없음)로 보고, 랏 수는 신규/재시도(priority=99999999) 분리 진단용.
  • 같은 공정 2회 표시: ModifiedGroup(공정그룹) 표시 때문 — 다른 WorkSeq의 별개 스텝(빌드업 다회 통과). sequence·CHASU 컬럼 병기로 해소.
  • 월별 집계: 생산은 최종 스텝 행(units_produced)·충족 테이블로만 — allocation 행 합산은 스텝 수만큼 곱해짐.
  • 제안(미구현): lot_status 라벨 컬럼(COMPLETED/FAILED/ABANDONED) — 위 함정 전부를 등호 필터 하나로 대체.

D.자주 나온 질문 (운영 Q&A)

질문답
SIM_allocation distinct 랏 ≈ 2.9만인데 실패도 2.2만?정상 — distinct는 «시도»이고 실패 랏의 실패 전 스텝도 남음. 성공은 units_produced>0 (~5천대), 나머지 소수는 수요 충족으로 중단된 랏 (§4.5).
실패가 왜 이렇게 많나?계획이 정직 용량의 ~6배 + 이월 재시도가 랏 수를 곱함. 헤드라인은 demand_shortfall (모델×월)로 (§4.5).
한 랏에 같은 공정이 두 번?공정그룹 표시 문제 — 다른 WorkSeq의 별개 스텝(다회 통과). sequence/CHASU 병기.
가상 랏 팝업이 비어 있음통계(실적) 패널은 VL에서 정의상 빈 것. 시뮬레이션 패널이 비면 관계 전파 필터 → lot_id 텍스트 변수 필터로 교체.
매출·마진이 전부 0/$?단가·마진 소스 부재 (§4.4). $ 표기는 원본 포맷 문자열 — 값은 KRW 스케일.
재고(+transit) 고려되나?됨 — OnHandLot FGI+FGI-TRN + 당월 출하가 forward-rolling으로 차감 (§4.1.1). 자재 재고는 분석용(할당 제약 아님).
차감이 그룹핑 모델 기준인가?구조는 그룹핑 그레인이나 소스 미충전으로 현재 개별 모델 기준 (§4.4).
HORIZON vs INSUFFICIENT 차이?같은 지각의 두 문턱 — 전자는 달력 초과(계획 문제), 후자는 90일 내 자리 없음(병목 문제). 집계 합산, 진단 분리 (§4.1.5).
